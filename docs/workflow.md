# 작업 흐름 설명서

이 문서는 `mouse-ui`를 앞으로 어떻게 개발할지 정리한 운영 기준이다.

초기에는 작은 버전마다 PR을 만들고 문서를 자주 갱신했다. 그 방식은 프로젝트 방향과 기본 구조를 잡는 데 도움이 됐지만, 지금부터는 기능 구현 속도를 더 중요하게 둔다.

## 기본 원칙

- 사용자는 큰 방향과 우선순위를 정한다.
- Codex는 기능을 작은 작업 단위로 나누고 직접 구현한다.
- 커밋은 기능 단위로 만든다.
- README와 docs는 매 기능마다 고치지 않고, 버전이나 큰 묶음이 끝날 때 정리한다.
- PR은 사용자가 확인해야 하는 큰 묶음이 됐을 때 만든다.

## 평소 작업 흐름

1. 사용자가 다음 목표를 말한다.
2. Codex가 현재 코드와 문서를 필요한 만큼 확인한다.
3. Codex가 기능 단위로 구현한다.
4. 각 기능이 끝날 때 빌드나 간단한 동작 확인을 실행한다.
5. 확인이 끝난 기능만 커밋한다.
6. 작업 묶음이 끝나면 README와 docs 상태를 확인한다.
7. 필요한 문서만 한 번에 갱신하고 별도 커밋한다.

## 커밋 기준

커밋은 목적이 하나여야 한다.

좋은 예:

- 텍스트 컴포넌트 추가
- 입력창 컴포넌트 추가
- 코드 복사 버튼 추가
- localStorage 저장 기능 추가
- v0.5.0 완료 문서 반영

좋지 않은 예:

- 여러 컴포넌트, 저장 기능, 문서 수정을 한 커밋에 넣기
- 동작 변경과 큰 리팩터링을 한 커밋에 섞기
- 문구 수정만 필요한데 기능 파일을 같이 고치기

## 문서 갱신 기준

문서는 기능 구현을 방해하지 않는 선에서 관리한다.

기능을 하나 추가할 때마다 README와 체크리스트를 고치지 않는다. 대신 아래 시점에 확인한다.

- 한 버전 목표가 끝났을 때
- PR을 만들기 전
- 프로젝트 방향이나 개발 방식이 바뀌었을 때
- 파일 구조나 책임 경계가 바뀌었을 때

문서 갱신이 필요하면 기능 커밋과 섞지 않고 문서 커밋으로 분리한다.

## 버전 운영

버전은 큰 목표를 나누기 위한 이름이다. 버전 때문에 작업 속도가 느려지면 안 된다.

- 버전 시작 전에 모든 문서를 완벽히 고치지 않는다.
- 버전 안에서는 기능 커밋을 빠르게 쌓는다.
- 버전 끝에서 체크리스트와 README를 정리한다.
- 작은 구조 개선은 필요하면 `v0.x.1`처럼 패치 버전으로 묶을 수 있다.

## PR 운영

PR은 매 기능마다 만들지 않는다.

PR을 만드는 시점:

- 사용자가 GitHub에서 확인하고 merge해야 할 때
- 버전 목표가 끝났을 때
- 여러 커밋을 하나의 검토 단위로 묶을 때

PR 전 확인:

- 작업트리가 깨끗한지 확인한다.
- 빌드나 핵심 동작 확인을 실행한다.
- README와 docs가 현재 상태와 크게 어긋나지 않는지 확인한다.
- PR 본문에 변경 내용, 확인한 것, 다음 작업을 적는다.

## 리팩터링 기준

구조 정리는 기능 구현을 더 빠르고 안전하게 만들기 위한 경우에만 한다.

리팩터링을 하는 좋은 시점:

- 새 컴포넌트를 추가할 때 수정해야 하는 파일이 지나치게 많아질 때
- 조건문이 여러 파일에 반복될 때
- 같은 데이터 정의가 여러 곳에 흩어질 때
- 저장, 복사, 우클릭 같은 기능을 붙이기 전에 책임을 정리해야 할 때

리팩터링도 가능한 한 목적별로 커밋한다.

## 현재 권장 흐름

현재 프로젝트는 `v0.5.0`에서 코드 복사와 저장/불러오기까지 진행했다.

다음 권장 흐름:

1. `develop`: `v0.5.0`까지의 기능을 통합한다.
2. `main`: 지금까지 만든 첫 저장 가능한 기준점으로 반영한다.
3. `v1.0.0`: 컴포넌트 정의, Inspector, codegen, 우클릭 메뉴, 삭제/복제, UI 사용성을 새 기준으로 재정의한다.

`v0.6.0`을 별도 버전으로 억지로 진행하지 않는다. 저장 가능한 상태를 `main`에 남긴 뒤, 다음 작업은 `v1.0.0`을 향한 새 출발로 다룬다.
